# 高密度工业自描述通信中间件设计文档
> **项目代号：Industrial Self-Describing Data Middleware（ISDM）**
>
> **核心理念：让工业通信从“配置数据点”转变为“传输数据模型”。**
>
> 本文是一份面向工程落地的总体设计文档，重点解决几十万到百万级工业数据点在实时采集、分发、结构化传输、配置维护以及跨进程/跨设备通信中的性能和工程复杂度问题。
>

---

## 1. 项目背景
工业现场存在大量高密度数据：

+ PLC 数据
+ 传感器数据
+ 电机/变频器状态
+ 保护装置数据
+ 过程控制数据
+ 电力设备模型
+ 机器人状态
+ AI/算法输入
+ SCADA/HMI 数据
+ 历史数据与实时数据

传统工业通信方案通常存在一个共同问题：

> **数据通信协议解决了“怎么传”，但没有很好解决“双方如何理解数据”。**
>

以 OPC UA、传统 DDS 使用方式以及大量自研 TCP/UDP 协议为例，工程现场经常需要维护：

```latex
设备配置
    ↓
点表
    ↓
变量名称
    ↓
变量类型
    ↓
地址映射
    ↓
Topic / Node / Tag
    ↓
发送端配置
    ↓
接收端配置
```

当系统只有几千个点时，这种方式尚可接受。

但是当系统规模达到：

```latex
100,000
300,000
600,000
1,000,000+
```

数据点配置、同步、升级和维护成本会迅速增加。

更严重的是，很多工业应用真正需要的并不是：

```latex
一个变量 = 一个通信对象
```

而是：

```latex
一个设备 = 一个结构
一个设备组 = 一个数组
一个过程 = 一个批量数据集
```

因此，本项目提出一种新的设计思路：

> **将“类型、对象、数据”作为通信系统的一等公民，通过 Schema 自动交换实现零人工配置的数据模型同步，同时针对超大规模数据场景采用 Batch、Delta、Bitmap、Zero-Copy、Shared Memory 等技术降低 CPU、内存和网络开销。**
>

# 2. 项目目标
## 2.1 核心目标
系统需要实现：

1. 支持 60 万以上数据点。
2. 架构上可扩展到百万级数据点。
3. 支持单点数据。
4. 支持结构体。
5. 支持数组。
6. 支持嵌套结构体。
7. 支持变长数组/Sequence。
8. 支持批量数据。
9. 支持全量 Snapshot。
10. 支持增量 Delta。
11. 支持自动 Schema Discovery。
12. 双方无需人工维护点表。
13. 数据发送后，对端能够自动理解数据结构。
14. 支持 Schema Version。
15. 支持 Schema Evolution。
16. 支持网络通信。
17. 支持同机 Shared Memory。
18. 尽可能实现 Zero Copy。
19. 避免百万级变量产生百万级 Topic / Publisher / Subscriber。
20. 尽可能减少 malloc、memcpy、锁竞争和系统调用。

---

# 3. 非目标
第一阶段不追求：

+ 完全兼容 OPC UA。
+ 完全兼容 IEC 61850。
+ 替代所有工业协议。
+ 自己重新发明一个通用 RPC 框架。
+ 使用 JSON 作为实时数据格式。
+ 通过 XML/YAML/JSON 配置几十万数据点。
+ 第一版本直接支持所有复杂业务语义。

项目重点是：

> **高性能、自描述、结构化、零配置的工业数据传输。**
>

# 4. 核心设计思想
整个系统建立在六个核心概念上：

```latex
                ┌───────────────┐
                │     Type      │
                │     类型       │
                └───────┬───────┘
                        │
                        ▼
                ┌───────────────┐
                │     Object    │
                │     对象       │
                └───────┬───────┘
                        │
                        ▼
                ┌───────────────┐
                │      Data     │
                │      数据      │
                └───────┬───────┘
                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
         Single       Batch       Delta
```

核心原则：

### 4.1 Schema 与 Data 分离
Schema 只在建立连接、Schema 更新或者对端请求时发送。

实时数据包不携带完整字段名称和类型定义。

例如：

第一次：

```latex
SCHEMA

TypeID = 100
TypeName = Motor

Field:
    1 -> speed -> FLOAT32
    2 -> current -> FLOAT32
    3 -> voltage -> FLOAT32
    4 -> status -> UINT32
```

之后数据：

```latex
DATA

TypeID = 100
ObjectID = 10001
Timestamp = ...
Payload = ...
```

这样可以避免每一个数据包重复携带 Schema。

# 6. Object Model
传统系统倾向于把 Variable 作为核心对象。

本系统建议：

> **Object 才是第一公民。**
>

例如：

```latex
Plant
 ├── Line01
 │    ├── Motor001
 │    ├── Motor002
 │    └── Motor003
 │
 └── Line02
      ├── Motor001
      └── Motor002
```

Motor：

```cpp
struct Position {
  double x;
  double y;
  double z;
};

struct Motor {
  float speed;
  float current;
  float voltage;
  float temperature;
  uint32_t status;
  Position position;
};
```

系统内部理解为：

```latex
Motor
 ├── speed
 ├── current
 ├── voltage
 ├── temperature
 ├── status
 └── position
      ├── x
      ├── y
      └── z
```

这样可以天然支持：

```latex
Motor001
Motor001.speed
Motor001.position
Motor001.position.x
Motor[0..999]
```

# 8. TypeID、FieldID、ObjectID
建议不要使用 16 bit 作为全局 ID。

60 万点已经超过：

```latex
65535
```

建议：

```latex
TypeID   = uint32
FieldID  = uint32
ObjectID = uint64
```

如果需要进一步扩展：

```latex
VariableID = uint64
```

---

## 8.1 Hash 的使用
可以使用：

```latex
Hash64(name)
```

加速：

```latex
Name -> ID
ID -> Descriptor
```

例如：

```latex
"plant1/line1/motor001"
        ↓
      Hash64
        ↓
ObjectID
```

但必须注意：

> Hash 只能用于快速索引，不能把“理论上极低概率冲突”当作协议正确性的依据。
>

Schema Registry 必须支持冲突检测。

# 9. Schema Descriptor
Schema 是整个系统最重要的数据结构之一。

建议：

```cpp
struct TypeDescriptor {
  uint32_t type_id;
  uint32_t version;
  TypeKind kind;

  StringView name;

  Vector<FieldDescriptor> fields;
};
```

Field：

```cpp
struct FieldDescriptor {
  uint32_t field_id;

  StringView name;

  uint32_t type_id;

  uint32_t offset;
  uint32_t size;

  uint32_t array_length;
};
```

注意：

> Wire Format 不应该直接依赖 C++ ABI。
>

不能简单地认为：

```cpp
sizeof(struct)
offsetof(struct, field)
```

就是协议定义。

协议需要明确规定：

+ Endianness
+ Integer Width
+ Float Format
+ Alignment
+ Padding
+ String Encoding
+ Array Layout
+ Struct Layout

这样才能保证：

```latex
x86
ARM
AArch64
不同编译器
不同语言
```

之间的数据一致性。

# 10. Schema Discovery
这是项目区别于传统配置式通信系统的核心。

启动流程：

```latex
Publisher
   │
   │ HELLO
   ▼
Subscriber
   │
   │ HELLO_ACK
   ▼
Subscriber
   │
   │ SCHEMA_REQUEST
   ▼
Publisher
   │
   │ SCHEMA
   ▼
Subscriber
   │
   │ SCHEMA_ACK
   ▼
Ready
```

之后：

```latex
DATA DATA DATA DATA DATA
```

Schema 不再重复发送。

---

# 11. Schema Cache
每一个 Node 都维护：

```latex
SchemaRegistry
```

逻辑：

```latex
TypeID
   ↓
TypeDescriptor
```

以及：

```latex
ObjectID
   ↓
ObjectDescriptor
```

建议使用：

```latex
Concurrent HashMap
```

或者读多写少场景使用：

```latex
RCU
```

避免实时数据线程频繁获取全局锁。

# 13. FieldID 的稳定性
FieldID 不应该因为字段顺序改变而改变。

错误设计：

```latex
Field 0 = speed
Field 1 = current
```

如果新增字段：

```latex
Field 0 = voltage
Field 1 = speed
Field 2 = current
```

旧数据全部失效。

正确：

```latex
1 = speed
2 = current
3 = voltage
```

新增：

```latex
3 = voltage
```

原来的：

```latex
1
2
```

保持不变。

# 18. Batch Data
60 万点场景中，Batch 是核心机制。

例如：

```latex
Batch
 ├── Motor001
 ├── Motor002
 ├── Motor003
 ├── ...
 └── Motor10000
```

数据：

```latex
┌──────────────────────────────┐
│ Batch Header                 │
│ Sequence                     │
│ Timestamp                    │
│ SchemaID                     │
│ ObjectCount                  │
└──────────────────────────────┘

┌────────────┐
│ Object 001 │
├────────────┤
│ Object 002 │
├────────────┤
│ Object 003 │
├────────────┤
│ ...        │
└────────────┘
```

---

# 19. Batch 中避免重复 ObjectID
如果：

```latex
Motor001
Motor002
...
Motor10000
```

每个对象都携带：

```latex
uint64 ObjectID
```

会产生大量额外开销。

可以在 Schema/Session 阶段建立：

```latex
ObjectID
    ↓
LocalIndex
```

例如：

```latex
Motor001 → 0
Motor002 → 1
Motor003 → 2
...
```

那么 Batch 可以变成：

```latex
StartIndex
Count
Payload
```

例如：

```latex
Motor[0..9999]
```

这样可以极大减少元数据开销。

# 20. Snapshot
Snapshot 表示：

> 当前整个数据模型的完整状态。
>

例如：

```latex
600,000 points
```

启动时：

```latex
Publisher
    ↓
Snapshot
    ↓
Subscriber
```

Subscriber 可以在一次或多次 Batch 中快速建立完整状态。

Snapshot 特别适用于：

+ 新订阅者加入
+ 断线重连
+ 数据恢复
+ 状态初始化

---

# 21. Delta
实时运行过程中，大多数情况下并不是所有数据都变化。

例如：

```latex
600,000 points
```

某个周期实际变化：

```latex
2,000 points
```

如果每次都发送全部：

```latex
600,000
```

是巨大的浪费。

因此支持：

```latex
Delta Update
```

---

# 22. Bitmap Delta
可以使用：

```latex
Bitmap
```

描述变化的数据：

```latex
00000000
00010000
00000001
...
```

然后只发送变化值：

```latex
Bitmap
+
Changed Payload
```

接收端：

```latex
Bitmap
   ↓
遍历变化位置
   ↓
写入本地 Object Store
```

对于大规模点表非常有效。

---

# 23. Delta 的进一步优化
如果变化数据具有连续性：

```latex
1000
1001
1002
1003
1004
```

可以使用 Range：

```latex
Start = 1000
Count = 5
```

因此 Delta 编码可以支持：

```latex
Bitmap
Range
Sparse Index
```

根据数据分布选择最优方式。

# 24. 数据布局
对于性能要求非常高的系统，不建议默认采用：

```latex
Object
  ├── Metadata
  ├── Field Metadata
  ├── Value
  ├── malloc
  └── malloc
```

而应尽量做到：

```latex
Flat Memory Layout
```

例如：

```latex
[Header][ObjectIndex][Timestamp][Payload]
```

避免大量指针跳转。

# 25. AoS 与 SoA
需要根据数据模式支持：

```latex
AoS
Array of Structures
```

以及：

```latex
SoA
Structure of Arrays
```

例如：

### AoS
```latex
Motor0:
 speed current voltage

Motor1:
 speed current voltage

Motor2:
 speed current voltage
```

### SoA
```latex
speed:
 s0 s1 s2 ...

current:
 c0 c1 c2 ...

voltage:
 v0 v1 v2 ...
```

对于：

+ 单设备处理
+ 网络协议

AoS 更自然。

对于：

+ 大批量计算
+ SIMD
+ AI
+ GPU
+ 数据分析

SoA 可能更有效。

因此内部 Data Engine 最好不要把 Wire Format 和 Application Memory Layout 强绑定。

# 26. Zero Copy
性能设计的目标之一：

```latex
Application
   ↓
Data Engine
   ↓
Transport
   ↓
Network
```

尽可能减少：

```latex
Application Buffer
      ↓ memcpy
Serialize Buffer
      ↓ memcpy
Socket Buffer
```

理想情况：

```latex
Application
     ↓
Shared / Registered Buffer
     ↓
Transport
```

对于 UDP/TCP，完全 Zero Copy 会受到操作系统和网络栈限制，因此实际目标应该定义为：

> **Minimize Copy，而不是盲目宣称 Zero Copy。**
>

---

# 27. Shared Memory
同机通信强烈建议支持 Shared Memory。

典型场景：

```latex
采集进程
    │
    ▼
Shared Memory
    │
    ├──── Algorithm
    ├──── SCADA
    ├──── AI
    └──── Recorder
```

使用：

```latex
Lock-free Ring Buffer
```

或者：

```latex
Multi-Reader Ring Buffer
```

减少：

```latex
syscall
context switch
memcpy
```

---

# 28. Ring Buffer
推荐核心结构：

```latex
Producer
   │
   ▼
┌─────────────────────────────┐
│ Slot │ Slot │ Slot │ Slot   │
└─────────────────────────────┘
   ▲       ▲       ▲
   │       │       │
 Reader A Reader B Reader C
```

每个 Slot：

```latex
Sequence
Timestamp
SchemaID
DataLength
Payload
```

通过 Sequence 判断：

```latex
是否可读
是否覆盖
是否丢帧
```

---

# 29. Lock-Free
实时数据路径尽可能避免：

```cpp
std::mutex
```

尤其避免：

```latex
600,000 point update
        ↓
600,000 mutex lock
```

建议：

```latex
SPSC
MPSC
MPMC
```

根据具体场景选择。

常见实时路径：

```latex
采集线程
   ↓
SPSC Queue
   ↓
Batch Aggregator
   ↓
Transport Thread
```

这样比所有模块共享一个大锁更可控。

---

# 30. Batch Aggregator
不要：

```latex
每一个变量变化
    ↓
立即 syscall
    ↓
send()
```

应该：

```latex
Point Update
Point Update
Point Update
Point Update
       ↓
Batch Aggregator
       ↓
Frame
       ↓
Transport
```

触发条件可以是：

```latex
时间阈值
数量阈值
字节阈值
```

例如：

```latex
max_points = 8192
max_bytes  = 64KB
max_delay  = 1ms
```

任意条件满足就发送。

# 31. 60 万点性能模型
假设：

```latex
600,000 points
每个点 4 bytes
周期 20ms
```

裸数据量：

```latex
600,000 × 4
= 2.4 MB / frame
```

50 frame/s：

```latex
2.4 MB × 50
≈ 120 MB/s
```

也就是约：

```latex
960 Mbps
```

还没有计算：

+ Header
+ Timestamp
+ ObjectID
+ Bitmap
+ 网络协议开销
+ 重传
+ 系统调用
+ 数据对齐

因此：

> 60 万点不是简单的“协议能不能传”的问题，而是一个端到端性能工程问题。
>

必须同时考虑：

```latex
CPU
Memory Bandwidth
L3 Cache
NUMA
NIC
Kernel
Socket Buffer
Packet Size
MTU
Copy Count
Serialization
Deserialization
```

# 33. Jumbo Frame
在受控工业网络中，可以支持：

```latex
MTU 9000
```

但协议不能依赖 Jumbo Frame。

必须同时支持：

```latex
MTU 1500
MTU 9000
```

网络层负责根据实际 MTU 分片。

---

# 34. UDP 与 TCP
建议第一阶段：

```latex
UDP
```

原因：

+ 低延迟
+ 用户可以控制可靠性
+ 更适合周期数据
+ 不存在 TCP Head-of-Line Blocking
+ 更容易实现 Batch

TCP 可以用于：

```latex
Schema
Control
Configuration
Low-rate reliable data
```

因此可以设计：

```latex
Control Channel
    TCP

Data Channel
    UDP
```

后续再支持统一 Transport。

---

# 35. 可靠性模型
不应该只有：

```latex
Reliable
Best Effort
```

建议定义：

```latex
BEST_EFFORT
RELIABLE
RELIABLE_ORDERED
SNAPSHOT_RECOVERY
```

例如：

### 实时遥测
```latex
BEST_EFFORT
```

旧数据丢了没有关系。

### 控制命令
```latex
RELIABLE_ORDERED
```

### 状态恢复
```latex
SNAPSHOT_RECOVERY
```

---

# 36. Sequence Number
每一个 Data Frame 都应该有：

```latex
Sequence
```

例如：

```latex
100
101
102
103
```

收到：

```latex
100
102
103
```

可以知道：

```latex
101 丢失
```

对于 Best Effort：

```latex
直接等待下一帧
```

对于 Reliable：

```latex
请求重传
```

# 37. Timestamp
建议支持：


至少保留：

```latex

```

避免数据到达通信中间件以后再打时间戳导致时间语义丢失。

如果数据源支持：

```latex

```

应该允许直接携带高精度时间。

# 39. Flags


使用 Bit Field：


# 40. Schema 压缩
Schema 本身不是高频数据，因此不需要过度优化。

但是如果：

```latex
600,000 objects
```

Schema 也可能很大。

因此支持：

```latex
Schema Compression
```

例如：

```latex
Zstd
LZ4
```

推荐：

```latex
Schema → Zstd
Data   → 默认不压缩
```

因为实时数据通常已经具有较高熵，而且压缩 CPU 成本可能抵消网络收益。

---

# 41. Data Compression
不要默认压缩所有数据。

应该根据：

```latex
CPU
Network
Data Entropy
Latency
```

动态选择。

例如：

```latex
LAN + 1Gbps
    ↓
No Compression

WAN + 100Mbps
    ↓
Compression
```

甚至未来可以支持：

```latex
Compression Threshold
```

只有：

```latex
Payload > N bytes
```

才压缩。

# 44. Cache Locality
60 万点场景下，CPU Cache 是非常重要的。

不推荐：


可能存在 NUMA。

# 73. Dirty Tracking

```latex

```


# 74. Dirty Tracking 的高级优化
如果数据源本身知道哪些字段发生变化：

```cpp
motor.speed = 100;
```

可以直接：

```latex
dirty(field_id = speed)
```

避免 Data Engine 再做：

```latex
old_value != new_value
```

比较。

对于 60 万点来说：

> **“谁修改，谁标脏”通常比周期性扫描 60 万点更高效。**
>

# 75. 避免全量扫描
错误：

```latex
每 20ms：

for i in 0..600000:
    if value[i] != old[i]:
        send()
```

这意味着：

```latex
每秒 30,000,000 次检查
```

更好的方式：

```latex
Update
   ↓
Dirty Queue
```

只记录变化点。

# 76. Dirty Queue
例如：

```latex
Update speed
    ↓
push(FieldID)

Update voltage
    ↓
push(FieldID)

Update status
    ↓
push(FieldID)
```

最终：

```latex
Dirty Queue
[1, 5, 7, 8, 100, ...]
```

Batch Aggregator 再把这些变化合并成 Bitmap/Range。

# 77. 重复更新合并
例如一个周期内：

```latex

speed = 101
speed = 102
speed = 103
```

不应该发送四次。

最终：

```latex

```

```latex

```

这样可以大幅减少网络压力。

# 157. 最核心的设计原则
整个项目最终可以浓缩成下面十条原则：

### 1. Model First
先定义数据模型，再考虑怎么传。

### 2. Schema Once
Schema 只交换一次或在变化时交换，不重复塞进实时数据。

### 3. Object First
通信对象优先于单个变量。

### 4. Batch First
大规模数据必须批量传输。

### 5. Delta First
实时场景优先发送变化数据。

### 6. Zero Copy Where Possible
减少 Copy，而不是盲目追求理论 Zero Copy。

### 7. Preallocation
实时路径尽量零动态内存分配。

### 8. Fast Path / Slow Path
复杂操作全部赶出高频数据路径。

### 9. Control Plane / Data Plane Separation
模型协商和实时数据完全解耦。

### 10. Benchmark Driven
所有高级优化都必须通过 benchmark 证明。

# 160. 为什么不应该将 DDS 作为核心依赖
本项目最初可以参考 DDS/FastDDS 的 Pub/Sub、Discovery、可靠传输等思想，但从产品架构上不应把 DDS 作为底层地基。

核心原因不是 DDS 不够优秀，而是本项目解决的问题与 DDS 的设计中心不同。

DDS 更偏向：

```latex
Topic
DataWriter
DataReader
QoS
Discovery
```

而本项目更偏向：

```latex
Schema
Object
Object Instance
Batch
Delta
Data Frame
```

例如 600,000 个数据点不应该自然地映射成 600,000 个 Topic、Writer 或 Reader，而应该组织为：

```latex
少量 Type
    ↓
大量 Object Instance
    ↓
Batch
    ↓
Delta / Bitmap
    ↓
Data Frame
```

因此：

> **DDS/FastDDS 可以作为参考实现、兼容 Adapter 或对比 Benchmark，但不应该成为 ISDM/ISDP 的核心依赖。**
>

这也意味着本项目可以独立定义自己的 Wire Protocol、Discovery、Schema Negotiation 和 Data Plane。



但仍然不需要：


# 165. 分层 Discovery
Discovery 不应该一次性广播整个数据模型。

```latex

       ↓
Level 2
Schema Discovery
       ↓
Level 3
Object Discovery
       ↓
Level 4
Data Stream
```

典型流程：

```latex
HELLO
  ↓
CAPABILITY
  ↓
SCHEMA
  ↓
SUBSCRIBE
  ↓
DATA
```

尤其需要避免：

```latex

    ↓
每个 Node 广播全部 600000 个对象
```

这会导致 Discovery 自己成为系统最大的流量来源。

Discovery 应该是轻量的，数据才是重量级的。

# 166. Schema Discovery
Schema 是本项目实现“无点表通信”的关键。

例如 Publisher 定义：

```cpp
struct Motor {
  float speed;
  float current;
  float voltage;
  uint32_t status;
};
```

系统生成：

```latex
TypeID
SchemaVersion
FieldID
FieldType
FieldOffset
FieldFlags
```

Subscriber 第一次收到：

```latex
SchemaID = 0x12345678
```

如果本地没有该 Schema：

```latex
Subscriber
    │
    │ SCHEMA_REQUEST
    ▼
Publisher
    │
    │ SCHEMA_RESPONSE
    ▼
Subscriber
```

Subscriber 将 Schema 缓存后，后续实时 DATA 只需要携带紧凑的 SchemaID/TypeID/ObjectID 信息，不再重复发送结构定义。

因此：

> **Schema 是低频元数据，Data 是高频数据；两者必须分离。**
>

# 168. Multicast 与 Unicast 的职责划分
建议明确规定：

```latex
Multicast
    ↓
Discovery / Broadcast-like Data

Unicast
    ↓
Point-to-Point Data
```

例如：

```latex
                 239.255.20.1
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        Node A        Node B       Node C
```

A 可以向组播地址发送公共状态数据。

而对于明确的订阅者：

```latex
Node A ──────────────> Node B
```

使用 Unicast 更容易控制带宽和可靠性。

最终可以由 API 暴露：

```cpp

PublishMode::kMulticast
PublishMode::kAuto
```

其中 `kAuto` 根据订阅关系和能力自动选择。

# 169. Discovery 不应该感知 60 万个数据点
这是一个非常重要的性能原则。

错误设计：

```latex
Node
  ↓
Discovery
  ↓
600000 Points
```

正确设计：

```latex
Node
 ├── Node Identity
 ├── Capability
 └── Schema Catalog
```

只有订阅关系建立以后，才进入：

```latex
Schema
   ↓
Object
   ↓
Data Stream
```

这样 Discovery 的复杂度主要与：

```latex
Node Count
Schema Count
Subscription Count
```

相关，而不是与：

```latex
Point Count
```

线性绑定。

这是系统能够扩展到百万级数据点的重要原因之一。

# 171. Snapshot / Delta / Recovery
新节点加入时，不应该等待数万个实时 Data Frame 才建立完整状态。

建议：

```latex
New Subscriber
      ↓
Schema Negotiation
      ↓
Snapshot
      ↓
Delta Stream
```

即：

```latex
Snapshot
    ↓
建立完整状态
    ↓
Sequence = N
    ↓
接收 N+1 之后的 Delta
```

断线恢复同理：

```latex
断线
 ↓
Sequence Gap
 ↓
判断缓存是否足够
 ├── 足够 → 请求缺失 Delta
 └── 不足 → 请求 Snapshot
```

这比单纯依赖“重新订阅然后等待数据自然恢复”更加确定。

# 172. Reliable 不应该成为唯一模式
工业数据天然存在两种语义：

### 状态型数据
例如：

```latex

Speed = 1200
Pressure = 1.3
```

通常更关注“最新值”。

这种场景可以使用：

```latex

```

### 事件型数据
例如：

```latex

Trip
Command
Sequence Event
```

可能要求：

```latex

ACK
Retransmission
```

因此协议应该支持：

```latex

Reliable
```

但不要让所有 60 万点都默认进入复杂 Reliable 状态机。

否则为了 1% 的关键事件，把另外 99% 的状态数据一起拖进重型机制，得不偿失。

也不应该被定义成：

> “一个自己实现的 DDS。”
>

更准确的定位应该是：

> **面向高密度工业实时数据的自描述数据协议与通信 Runtime。**
>

核心能力：

```latex
Zero Configuration
Self Describing
Native Struct
Native Array
Batch
Delta
Snapshot
Multicast Discovery
Unicast Data
Shared Memory
High Density
```

最终实现：

```latex
传统工业通信：

数据
 ↓
点表
 ↓
人工配置
 ↓
映射
 ↓
协议
 ↓
数据
```

本项目：

```latex
Data Model
    ↓
Schema
    ↓
Automatic Discovery
    ↓
Schema Negotiation
    ↓
Direct Data Transfer
    ↓
Remote Object
```

即：

> **让数据模型本身成为通信协议的一部分。**
>

而 Discovery 负责让节点认识彼此，Schema 负责让节点理解数据，Data Plane 负责让数据以最高效率流动。

这三者组合起来，才是本项目区别于传统工业通信中间件的核心。
